## Deviazioni dal piano
- Il riuso del prefisso del passo 6 non può passare dal re-render del template (C4/scheda): il template GGUF di Gemma 4 rimuove i thought channel dalle risposte passate (`strip_thinking`) e non rimette il reasoning dei turni passati (`thinking_gate`), quindi la risposta thinking non compare MAI nel re-render e `text.startswith(text_prev + risposta)` non può valere (job S7-3). Il riuso in `cli.py` è a livello di token (`continuation_ids`, b2698fd): la chiusura del turno assistant costruita come il template la emetterebbe + blocco utente preso dal template stesso. Il contesto mantiene i thought delle risposte precedenti (il modello rivede il proprio ragionamento, come nei loop agentici), quindi il prompt del turno k+1 differisce dal re-render canonico HF/llama.cpp (che li scarta). Impatto su S8: se il server riusa la stessa logica, scelta identica; la regressione C10 non tocca la chat.
- C4 dice «gruppo gloo»: il gruppo è sempre gloo/CPU, ma su torch 2.15.0+xpu
  `dist.new_group(backend="gloo")` è inutilizzabile (binding al device del
  gruppo di default, xpu:0, rifiutato dal backend gloo). `parallel.py` lo
  costruisce con il creator privato `_new_process_group_helper(..., device_id=None)`
  (commit 28f69df): stesso gruppo che `new_group` creerebbe, senza binding;
  `broadcast_obj` usa poi `dist.broadcast_object_list` su CPU. Meccanismo
  privato, legato alla torch installata sul PC.

## Note per le sezioni successive
- `cli.py chat`: gli ids del turno k+1 continuano i token della sessione, mai
  ricostruiti dal testo. Tre vie, in ordine: (1) il re-render del template
  estende esattamente `prompt_prev + risposta` (e la risposta ha riempito il
  contesto) → stop id + coda; (2) `continuation_ids` (b2698fd): risposta
  chiusa dallo stop `<turn|>` (rigiocato) o tagliata da `-n`
  (`session.last_truncated`) → chiusura del turno assistant come il template
  la emetterebbe (`\n<channel|>` se il thought è ancora aperto, poi
  `<turn|>\n`) + blocco utente di `render([nuovo utente], True)` tolta la
  testa comune `render([], False)` (BOS+blocco system); (3) altrimenti
  re-encode completo (il `Session.prefill` fa il reset da solo). Con Gemma +
  `enable_thinking=True` e `-n` 128 le risposte si tagliano sempre a metà
  thought: vale SEMPRE la via 2 (la 1 non può valere, Deviazioni); senza via 2
  i turni 2+ hanno l'amnesia delle risposte (job S7-3).
- `[stats] prompt new A/B`: A = token che il prefill ricalcola, B = token del
  contesto (risposte precedenti incluse). Verifica riuso (job S7-4, esito: verificata): turno 1
  A==B (~29 senza `--system`), turni 2+ A ≈ chiusura+blocco utente (~20 <60),
  B cresce di ~128+15/turno (la risposta resta nel contesto). Misurato:
  29/29, 18/175, 17/320.
- Il template GGUF di Gemma 4 emette `{{ bos_token }}` (stringa `<bos>`) a inizio
  prompt: `chat.render` lo mantiene (semantica HF), llama.cpp invece lo rimuove
  (golden `template.json` senza BOS → test confronta con `bos + prompt`). Va
  sempre tokenizzato con `add_bos=False`; il default `add_bos=True` lo
  raddoppierebbe.
- Golden `template.json` = llama-server con kwargs {} → corrisponde a
  `enable_thinking=True` nel template jinja (con `enable_thinking=False` il
  template aggiunge il suffisso `<|channel>thought...` e salta il blocco system
  senza message system). La chat CLI usa `enable_thinking=True`: è l'unica che
  rende il prompt del turno successivo un'estensione esatta di quello
  precedente (richiesta dal riuso del prefisso).
- Template jinja usa: `messages`, `add_generation_prompt`, `tools` (default
  `[]`), `enable_thinking`, `bos_token` (1 volta), `raise_exception` (1 volta).
  `render` passa `bos_token`/`eos_token` quando riceve un GGUF.

## Problemi aperti
- (job S7-2, RISOLTO) `dist.new_group(backend="gloo")` non può creare il gruppo gloo di C4
  su torch 2.15.0+xpu quando il gruppo di default è legato a un device (`init_process_group("xccl", device_id=xpu:0)`): `_new_group_with_tag` eredita `bound_device_id` e `pg._get_backend(xpu:0)` su un backend gloo solleva «No backend type associated with device type xpu»; passare `device_id=cpu` è esplicitamente vietato (`AssertionError: Mismatched bound device`). Fix in preparazione: creare il gruppo con `_new_process_group_helper(..., device_id=None)` (lo stesso creator che torch usa per `new_group`, senza il binding di device) e usare `broadcast_object_list` su CPU (fix 28f69df, test CPU a 2 rank verdi). Verificata: la chat di S7-2 gira 3 turni con exit 0.
