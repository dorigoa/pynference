## Note per le sezioni successive
- `cli.py chat`: il turno k+1 riusa i token del turno k se il re-render del
  template estende esattamente `prompt_prev + risposta` e la risposta ha
  riempito il contesto: chiusa da uno stop id (`session.last_stop`, che va
  aggiunto ai token) o tagliata da `-n` (`session.last_truncated`: tutto ciò
  che è stato alimentato è anche ciò che è stato restituito, nessun token da
  aggiungere). Altrimenti re-encode completo (il `Session.prefill` fa il reset
  da solo). Con `enable_thinking=True` le risposte non finiscono entro `-n`
  128, quindi il riuso passa SEMPRE da `last_truncated`: senza questa fix
  (job S7-2) la chat non riusava mai niente.
- `[stats] prompt new A/B`: A = token che il prefill ricalcola, B = token totali
  del prompt (risposta inclusa: turno k → ~157, poi +~140/turno). Verifica
  riuso: turno 1 A==B (prompt intero), turni 2+ A≈coda (<60).
- Il template GGUF di Gemma 4 emette `{{ bos_token }}` (stringa `<bos>`) a inizio
  prompt: `chat.render` lo mantiene (semantica HF), llama.cpp invece lo rimuove
  (golden `template.json` senza BOS → test confronta con `bos + prompt`). Va
  sempre tokenizzato con `add_bos=False`; il default `add_bos=True` lo
  raddoppierebbe.
- Golden `template.json` = llama-server con kwargs {} → corrisponde a
  `enable_thinking=True` nel template jinja (con `enable_thinking=False` il
  template aggiunge il suffisso `<|channel>thought...` e salta il blocco system
  senza message system). La chat CLI usa `enable_thinking=True`: è l'unica che
  rende il prompt del turno successivo un'estensione esatta di quello
  precedente (richiesta dal riuso del prefisso).
- Template jinja usa: `messages`, `add_generation_prompt`, `tools` (default
  `[]`), `enable_thinking`, `bos_token` (1 volta), `raise_exception` (1 volta).
  `render` passa `bos_token`/`eos_token` quando riceve un GGUF.

## Problemi aperti
- (job S7-2, RISOLTO) `dist.new_group(backend="gloo")` non può creare il gruppo gloo di C4
  su torch 2.15.0+xpu quando il gruppo di default è legato a un device (`init_process_group("xccl", device_id=xpu:0)`): `_new_group_with_tag` eredita `bound_device_id` e `pg._get_backend(xpu:0)` su un backend gloo solleva «No backend type associated with device type xpu»; passare `device_id=cpu` è esplicitamente vietato (`AssertionError: Mismatched bound device`). Fix in preparazione: creare il gruppo con `_new_process_group_helper(..., device_id=None)` (lo stesso creator che torch usa per `new_group`, senza il binding di device) e usare `broadcast_object_list` su CPU (fix 28f69df, test CPU a 2 rank verdi). Verificata: la chat di S7-2 gira 3 turni con exit 0.
