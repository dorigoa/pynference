## Note per le sezioni successive
- `server.py`: prompt = `tokenizer.chat_prompt(messages)` (thinking=False,
  suffisso `<|channel>thought…` come `generate --chat`) + `tok.encode(text)`
  (default `add_bos`): percorso IDENTICO a `pynference.generate --chat`, quindi
  una richiesta greedy coincide con `cli generate` stesso prompt/temp. NON usa
  `chat.render` con `enable_thinking=True` (via della chat CLI, che serve al
  riuso di prefisso tra turni; il server tratta ogni richiesta come
  conversazione nuova, e `Session.prefill` fa il reset da solo).
- Streaming byte-esatto con la risposta normale: per ogni token il server flusha
  `tok.decode(acc[:cut])` (cut = stessa regola di `Session._stop_string_cut`) o,
  senza cut, `tok.decode(acc)` meno il suffisso che è prefisso proprio di una
  stop string (`_unflushable_len`); il resto arriva dal flush finale.
- Se il client SSE si disconnette a metà, `on_token` ingoia l'errore e la
  generazione continua fino in fondo: interromperla solo sul rank 0 sfaserebbe
  i rank (KV cache diversi). Default sampling dal GGUF (come cli); `max_tokens`
  default 512 (`-n` del server); `max_completion_tokens` ha la precedenza.
- Spegnimento: SIGINT/SIGTERM handler sul rank 0 → `stopping=True` + shutdown
  HTTP; poi `with gen_lock` (fine richiesta in corso) → broadcast `stop` →
  `tp.close()`; i rank follower escono da soli appena arriva `stop`.
- Porta: 8090 (8000 Strata, 8091 llama.cpp nei job); test sempre su 127.0.0.1.
- `cli generate` mescola su stdout la risposta con i progress del caricatore
  (`models/gemma4.py` stampa «  loaded N/M layers») e i warning CCL di
  oneAPI: chi cattura stdout come testo pulito deve filtrarli (vedi S8-2.sh).
  `cli chat` invece manda i log su stderr.
